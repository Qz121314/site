# 开发阶段与交付计划

本文档定义主项目的实施顺序。核心原则是先建立稳定的数据和发布边界，再开发依赖这些边界的用户界面，避免先接临时 API 后重复改造。

## 1. 首个可交付闭环

第一版必须优先完成以下完整链路：

```text
中文后台登录
→ 创建频道、分类和标签
→ 创建门店与 Listing
→ 上传封面和相册
→ 编辑 English / Español
→ 发布并生成 R2 快照
→ /en 与 /es 读取正式快照
→ 列表筛选和详情页
→ 联系客服或外部跳转
```

在这条闭环稳定前，不优先开发复杂仪表盘、完整广告系统、第三方客服适配器或大量装饰性页面。

## 2. 阶段 0：工程初始化

目标：形成可构建、可测试、可部署的 Monorepo 骨架。

任务：

- [ ] 初始化 pnpm workspace；
- [ ] 创建 `apps/storefront`；
- [ ] 创建 `apps/admin`；
- [ ] 创建 `apps/worker`；
- [ ] 创建共享 packages；
- [ ] 配置 TypeScript、ESLint、格式化和严格类型检查；
- [ ] 配置 Vitest 和 Playwright；
- [ ] 配置移动优先设计令牌、断点和基础组件；
- [ ] 配置 Storefront Manifest、Service Worker 和图标管线；
- [ ] 确保 Service Worker 不覆盖 `/admin` 和 `/api`；
- [ ] 配置 Wrangler、环境和绑定类型生成；
- [ ] 配置结构化日志、请求 ID、错误响应和健康检查；
- [ ] 配置 CI；
- [ ] 配置 main 自动部署和 smoke test；
- [ ] 建立 Preview 与 Production 资源隔离约定。

阶段完成标准：

- 三个应用可以独立构建；
- Worker 可以在本地运行并提供健康检查；
- Storefront 和 Admin 可通过统一 Worker 路由访问；
- CI 可执行 lint、typecheck、unit test 和 build；
- PWA 基础文件可通过自动校验。

## 3. 阶段 1：领域模型、数据库、管理员鉴权与审计

目标：建立稳定的数据边界和后台安全基础。

任务：

- [ ] 固定 Channel、Category、Tag、Listing、Store 领域模型；
- [ ] 建立 D1 schema 和迁移机制；
- [ ] 建立实体表与翻译表；
- [ ] 建立管理员、角色、权限和管理员会话；
- [ ] 建立 RBAC 中间件和权限矩阵；
- [ ] 建立内容状态和发布状态；
- [ ] 建立审计日志；
- [ ] 建立软删除字段、回收站查询和 deletion jobs；
- [ ] 建立幂等键机制；
- [ ] 建立数据库备份、导出和恢复演练脚本；
- [ ] 建立种子管理员和本地演示数据；
- [ ] 为外键、状态、时间和常用筛选字段建立索引。

测试随本阶段完成：

- 迁移前进和回滚策略测试；
- RBAC 权限矩阵测试；
- 管理员会话失效测试；
- 审计日志测试；
- 软删除、恢复和唯一约束测试；
- 批量操作事务测试。

阶段完成标准：

- 管理员可以安全登录；
- 具备最小 CRUD API；
- 所有写操作可审计；
- 数据库可从备份恢复；
- 不存在普通用户账号依赖。

## 4. 阶段 2：R2 媒体系统

目标：完成安全、可追踪、可回收的媒体上传闭环。

任务：

- [ ] 配置 Preview 和 Production 独立公开/私有 Bucket；
- [ ] 建立上传预约接口；
- [ ] 分配受控对象 Key；
- [ ] 实现客户端图片压缩；
- [ ] 实现服务端对象确认；
- [ ] 校验 MIME、扩展名、大小、尺寸和校验和；
- [ ] 定义卡片、详情、门店和 Banner 图片规范；
- [ ] 处理 EXIF 和定位信息；
- [ ] 建立 `media_assets` 和引用关系；
- [ ] 实现封面优先、相册第一张回退逻辑；
- [ ] 实现内容哈希去重；
- [ ] 实现未确认、无引用和替换后对象的延迟清理；
- [ ] 实现 R2 公开基础域名后台配置和连接测试。

测试随本阶段完成：

- 非法 MIME 和扩展名；
- 超大文件和异常尺寸；
- 未授权上传；
- 对象不存在或校验和错误；
- 重复上传；
- 引用中的图片禁止物理删除；
- 垃圾回收幂等性。

阶段完成标准：

- 数据库只保存对象 Key；
- 上传失败不会产生永久垃圾对象；
- 图片显示规则和尺寸规范可自动验证。

## 5. 阶段 3：最小公开发布管线

目标：让用户端从第一天读取正式快照，而不是临时 D1 列表 API。

任务：

- [ ] 实现 `publish_jobs` 和互斥发布锁；
- [ ] 实现发布幂等键；
- [ ] 实现发布前英语和西班牙语完整度校验；
- [ ] 从 D1 生成版本化公开 JSON；
- [ ] 生成 manifest 和文件哈希；
- [ ] 写入 R2 版本目录；
- [ ] 验证所有文件存在且校验通过；
- [ ] 最后切换 `current.json`；
- [ ] 实现发布失败恢复；
- [ ] 实现版本列表和一键回滚；
- [ ] 实现旧版本保留和延迟清理；
- [ ] 建立发布日志和错误报告；
- [ ] 实现 Preview 环境独立指针。

测试随本阶段完成：

- 重复提交同一发布任务；
- 并发发布；
- 中途写入失败；
- 指针切换失败；
- 文件缺失或哈希不匹配；
- 旧客户端读取新快照；
- 回滚和再次发布；
- Preview 不得覆盖 Production。

阶段完成标准：

- 发布操作不存在半发布状态；
- `current.json` 只指向完整有效版本；
- 回滚不需要重新生成内容；
- 快照格式符合 `docs/public-snapshot-contract.md`。

## 10. 独立客服系统

完整客服系统继续作为另一个项目，在主项目稳定后开发：

- 多租户；
- Site 和域名绑定；
- 客服账号和工作台；
- 移动优先客服坐席 PWA；
- WebSocket 和 Durable Objects；
- 游客咨询限额；
- 消息加密和销毁；
- 客服队列、分配、转接和关闭；
- API、SDK 和 Webhook；
- 与主项目 `custom` Provider 对接。

主项目不得提前复制一套临时完整聊天后端。

## 11. 延后接入项

以下能力按实际需求接入，不作为阶段 0 的强制依赖：

- KV；
- Analytics Engine；
- Turnstile；
- Web Analytics；
- 完整运营仪表盘；
- Chatwoot 和 TalkJS 适配器；
- 普通用户账号系统；
- 深色模式；
- 独立客服系统。

“延后”不代表删除接口边界，而是不在首个闭环前投入实现成本。

## 12. 持续质量规则

测试、备份、监控和安全不属于最后一个阶段，而是每个阶段的完成条件。

每次合并到 main 前至少执行：

```text
install
→ lint
→ typecheck
→ unit tests
→ contract tests
→ build
→ migration validation
→ PWA validation
→ targeted Playwright tests
```

部署后执行：

```text
health check
→ storefront smoke test
→ admin smoke test
→ API smoke test
→ current.json validation
→ PWA installability check
```

高风险数据库迁移采用：

```text
先新增
→ 双写或迁移数据
→ 验证
→ 切换读取
→ 最后删除旧结构
```

## 13. 范围控制

开发中出现新需求时，按以下顺序判断：

1. 是否影响首个交付闭环；
2. 是否改变领域模型或公开快照协议；
3. 是否引入新的安全、隐私或运维责任；
4. 是否可以作为独立模块延后；
5. 是否需要同步修改 README 和架构文档。

任何会改变数据边界、发布协议、客服职责或 PWA 缓存规则的需求，都必须先更新架构文档，再实施代码。
